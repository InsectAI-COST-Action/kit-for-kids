An insect camera a child can actually use

A battery-powered camera that watches an insect enclosure for an hour, then tells its story on any computer — no app, no server, no internet.

Pilot camera software system — objectives, functionality and method Tom August · 21 August 2026

01 · Objectives

What I set out to build

Six commitments, written down before any code. Each one rules something out — which is what makes them useful.

  • 01Runs itselfPower on, walk away, collect unattended for up to an hour.
  • 02Never loses dataPulling the battery mid-session must not corrupt what came before.
  • 03No software to installCard into a laptop, double-click one file. Fully offline.
  • 04Made for childrenThe first screen is a welcome, not a configuration panel.
  • 05AI that stays honestAlways labelled a guess — never presented as a species identification.
  • 06Open and reproduciblePinned toolchain, documented schemas, an auditable card.
The hardest constraint is #3. It has to work on a locked-down school laptop with no internet and no admin rights — which rules out every conventional web approach and shapes the whole architecture.

02 · Functionality

Autonomous capture

The board is given no instructions in the field. Everything it needs is on the card, and the sequence is the same every time.

  1. Boot and self-checkConfirm the sensor and PSRAM are present; fail visibly rather than loop.
  2. Read config.jsonInterval, quality, duration, motion mode. Missing or invalid falls back to documented defaults.
  3. Open the sessionNew run ID, a manifest recording the settings actually in force.
  4. Warm up for five secondsLets sensor exposure settle before the first real frame.
  5. Capture on a fixed clockOne frame per second, rebased if a frame runs long — never a growing backlog.
Settings are a short list, not a free-for-all. The dashboard can only offer combinations the firmware knows it can honour, and the firmware re-validates on boot.

03 · Method

Writing data that survives being unplugged

Children stop the camera by pulling the battery cable. That is the intended design — so every write assumes power can vanish mid-operation.

Per frame
One row written and flushed to captures.csv immediately — nothing is held in memory waiting for a clean shutdown
Per image
Written to a temporary name, then atomically renamed. A half-written JPEG never acquires a real filename
Directory load
Images sharded 100 to a folder, so write time stays flat deep into a long session
On next boot
An unfinished run is detected and marked interrupted, never silently resumed

04 · Method

Keeping only what moves

An hour at one frame per second is 3,600 images, most of them identical. Optional motion triggering keeps the interesting ones — without ever hiding that a check happened.

  1. Grab a tiny preview160×120 greyscale — cheap enough to take every scheduled check.
  2. Score against the previous previewSplit into an 8×6 tile grid and compare tile by tile, so a small local movement is not diluted by the whole frame.
  3. Correct for overall brightnessA cloud passing shifts every tile equally; that shift is subtracted so lighting changes do not read as motion.
  4. Compare to a fixed thresholdAbove it, switch the sensor to full quality and save. Below it, log the check and save nothing.
  5. Settle, then re-baselineAfter a full capture the sensor re-adjusts, so two frames are discarded before the next comparison.
Every check is logged either way. A skipped frame still writes a row with its score, so the record is complete and the threshold can be reviewed after the fact — the data never quietly disappears.
Still experimental. Retaining every frame remains the default; motion mode is opt-in until it has been through physical acceptance testing.

05 · Functionality

The dashboard travels on the card

The card carries its own viewer. Put it in any Windows or Mac laptop, double-click dashboard.html, and it opens straight from the card.

Camera settings
Writes a new config.json back for the next run
Adult details
Frame search and per-capture records, deliberately tucked away

How it loads without a server

A browser opening a local file cannot fetch other files freely. So the firmware writes its data as small JavaScript chunk files that the page simply includes — 100 records each, closed and promoted atomically as they fill.

One damaged chunk cannot take the page down. Each loads independently; the rest still display. The raw CSV remains the authoritative record behind them.
Nothing is uploaded, ever. No network calls, no CDN, no telemetry — the page works with the machine offline.

Asking the computer to look

Two deliberate constraints

It runs on the laptop, not the camera. These models need far more memory than the board has. Keeping the device model-free protects capture reliability — the camera's job is to capture, nothing else.
The language is held firmly. Results are described to children as possible-insect clues. No species claims and no validated-detection language until the evidence supports it — the wording is a design decision, not a caveat.

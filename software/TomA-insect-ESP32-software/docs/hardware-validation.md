## Finding: `SD.totalBytes()` reports a wrong value on every normal (cold) boot (29 August 2026)

Found while adding a storage-remaining metric to the dashboard front page. `SdStorage::totalBytes()` (a thin wrapper over `SD.totalBytes()`) reports a value roughly double the card's actual capacity (`7,948,206,080` vs. the correct `3,653,238,784`, confirmed via the dev-bridge `DF` command on the same physical mount) - but only on the **very first `SD.begin()` call since power-on**. Any later, separate `SD.begin()` call in the same power cycle (e.g. the dev-bridge's `MOUNT` command, run after a session has stopped) reports correctly. The wrong value is stable for the entire session, not just the initial read - re-checked after a chunk promotion (~100 captures in) with no change. `SD.usedBytes()` is unaffected throughout.

Three fixes tried, all firmware-only, none successful - recorded so they are not retried without new information:
1. **Not an SPI clock effect.** Both the wrong cold-mount reading and the correct warm-mount reading were confirmed at the same negotiated 25 MHz.
2. **A throwaway `SD.begin()`/`SD.end()` cycle before the real mount** (hypothesis: "warm up" the reporting without changing real mount behaviour) - no effect, value unchanged.
3. **`SD.cardSize()` instead of `SD.totalBytes()`** - a completely different code path (`sdcard_num_sectors()`/`sdcard_sector_size()`, reading the card's own registers, versus `totalBytes()`'s `f_getfree()` call into FATFS volume metadata) - reproduced the identical wrong value. This is the most informative negative result: it points at the underlying SD driver's own card-geometry detection being wrong on a cold mount, not at anything in the Arduino-level FAT filesystem layer, which is beyond what could be safely investigated further without lower-level ESP-IDF tooling or physical access.

**Practical impact:** every normal deployment reads this value from a cold boot - nobody naturally triggers a second `SD.begin()` before looking at the dashboard - so this would be wrong in every real use case, not an edge case. The dashboard's new storage-remaining metric was built and works correctly end-to-end, but `DashboardWriter::writeSummary()` deliberately does not populate `sdTotalBytes`/`sdUsedBytes` until this is fixed, rather than ship a number known to be wrong; the dashboard shows "Soon" for that metric in the meantime and needs no further change once a fix lands. Left as an open firmware/driver-level investigation for whoever has the tooling to go deeper (live heap/register debugging, or checking whether this is a documented erratum for this card/ESP-IDF SD driver combination).

## Incident: FAT32 root-directory corruption after normal power-off (21 August 2026)

After a successful motion-mode test run (`run_000002`, the shard-directory fix validation — 299 checks, 31 saved images, 0 storage errors during capture), the card was stopped normally by disconnecting the battery cable and moved to a card reader. On the next mount, Windows reported the volume as a healthy FAT32 filesystem (correct size, no dirty bit), but the root directory itself was corrupted: every real file and folder (`dashboard.html`, `config.json`, `raw/`, `images/`, `data/`, `system/`) had been replaced by a single garbled, zero-length pseudo-entry that both `attrib` and PowerShell's file APIs treated as a broken symbolic link.

This is first-hand confirmation of the FAT32 write-safety risk already flagged in `docs/next-session.md` and the project brief: the filesystem's own directory/FAT metadata is not written atomically, and the documented stop method (disconnect the battery cable) gives no opportunity for a controlled unmount. The firmware's per-frame atomic-rename writes protected individual images and CSV rows during the session itself (no corruption was ever observed while captures were running, across today's session or the prior one), but this incident shows the risk sits one level up, in the filesystem's own directory table, which firmware-level write discipline cannot fully protect against.

Recovery attempted: `chkdsk /f` repaired the volume and recovered 2,007 orphaned cluster fragments (275 MB) into `FOUND.000`. 1,913 of those fragments began with a valid JPEG signature, so most of the recovered data was genuine photo content, but the recovery was fragment-level (unordered ~32 KB clusters, most JPEGs span several), carried no filenames or session metadata, and only one fragment retained readable `captures.csv` header text. Given the run was this week's test data rather than irreplaceable field data, reconstruction was not attempted; the card was reformatted clean instead.

**Open follow-up:** this remains an unresolved hardware-level gap, not something firmware alone can fully close (see the physical power hold-up circuit note in the project brief). It also means a corrupted card is a real, observed failure mode for the pilot, not just a theoretical one — worth factoring into the one-hour endurance test and any operator-facing guidance on stopping the camera safely.

## Finding: one-hour pilot runs consistently fall ~10-15 images short of 3,600; dark-scene-JPEG-size theory tested and not confirmed (28 August 2026)

**Dark run** (`run_000041`), driven entirely over the serial [dev bridge](dev-bridge.md) while unattended: the card had drifted to a stale 5-minute trial `config.json` (`max_session_seconds: 300`) from earlier testing, corrected to the repository pilot default and applied with `reboot`. Ran its full `max_session_seconds: 3600`, self-finished cleanly, no reboot/storage error/corruption. **Captured 3,589/3,600** - 35 full shards plus a partial final shard (89 images). Averaged ~190 KB/image, well above the ~87 KB reference, in a dark room. Working theory at the time: larger, noisier dark-scene JPEGs push some per-frame writes over the 1,000 ms budget, and the schedule never fully catches up over an hour.

**Daylight run** (`run_000050`), same protocol, run after the room had light again: **captured 3,585/3,600** - *slightly worse*, not better, despite JPEGs averaging 87,656 bytes (right on the ~87 KB reference, confirming lighting was the reason the dark run's files were oversized). `interval_mean_ms=1004` (on target) but `interval_max_ms=2363` - a *larger* worst-case gap than the dark run's 2,085 ms. Both runs' stats came from the on-device `AUDIT` command (see [dev-bridge.md](dev-bridge.md)), which also confirmed `csv_completed` exactly matches the on-disk image count in both cases - the shortfall is real capture loss, not a logging/audit discrepancy.

**Conclusion: the dark-scene-JPEG-size theory is not confirmed.** Smaller files did not close the gap or reduce the worst-case interval - if anything both got slightly worse. The ~0.3-0.4% shortfall looks like a more fundamental, lighting-independent cadence issue (`AUDIT` only reports mean/max interval, not the full distribution or its correlation with individual frame write time, so the exact mechanism - occasional SD/filesystem housekeeping cost, chunk-promotion overhead, or something else - remains open). Worth revisiting once the write-path reduction work in `next-session.md`'s SD-performance section has progressed further, or with finer-grained per-frame instrumentation than `AUDIT` currently provides.

## Finding: image-quality review, daylight run 28 August 2026 (`run_000050`)

Two real JPEGs pulled from the card and viewed directly (`shard_0001/..._img_1.jpg`, session start; `shard_0019/..._img_1850.jpg`, ~31 minutes in), subject a printed photo of ants placed under the camera, viewed top-down through the enclosure's corner mounts:

- **Focus:** Soft throughout both images, consistently - the enclosure's own corner brackets are equally soft, so this reads as a fixed-focus/depth-of-field characteristic at this camera-to-subject distance, not something specific to the subject or session timing.
- **Exposure:** Acceptable in both, not blown out or underexposed, though slightly flat/low-contrast.
- **Colour - a real finding:** `img_1` (session start) has a distinct **green/cyan colour cast** across the whole frame. `img_1850` (~31 minutes later) is close to neutral white/grey. This looks like auto-white-balance settling in over the first part of a session rather than a fixed characteristic - worth checking whether this affects data quality specifically in the first few minutes of every run, and whether it's consistent enough to warn about or correct for.
- **Small-insect detail:** Ant body outlines are identifiable in both images, but fine features (legs, antennae) are not resolved at this quality/distance. **Caveat:** the subject was a printed photo, not live insects, so print quality is a real confound here - this is not a clean test of live small-insect detail capture, which still needs doing.

## Fix attempted: session-start white balance - did not resolve it (28 August-29 August 2026)

The user reported the session-start green cast (finding above) as a repeated problem, not a one-off. Investigating `src/camera_service.cpp` found the driver never explicitly configured AWB, relying entirely on `esp_camera_init()` defaults, and `src/main.cpp`'s 5-second camera warm-up was a bare `delay(kCameraWarmupMs)` - the sensor was never actually asked to produce a frame during that window. AWB/AEC algorithms converge on captured frames, not elapsed time, so a pure delay gives them zero iterations to work with; this is a strong candidate for why 5 seconds did nothing but ~1,800 real captures (30 minutes at 1 FPS) did.

**Fix:** `CameraService::initialiseCamera()` now explicitly calls `set_whitebal(1)`, `set_awb_gain(1)`, `set_wb_mode(0)` (auto, not a fixed preset) after every sensor init, and exposes `whiteBalanceStatus()` for boot-log diagnostics. `setup()`'s warm-up (`kCameraWarmupMs`, now 15,000) replaced the bare `delay()` with an active loop that calls `camera.capture()`/`camera.release()` repeatedly until the deadline, giving AWB/AEC real frames to converge on before the first frame is ever retained. Costs nothing against the 3,600 s capture budget - `session_started_ms` is only set after warm-up completes.

**Functionally verified 28 August 2026** (smoke test only, not a colour-quality trial - it was evening): built, flashed, and the boot log confirmed the mechanism works as intended - `awb=1 awb_gain=1 wb_mode=0` both before and after warm-up, and **85 real frames pumped** in 15 s (versus zero previously). A short test session then captured normally with no crashes, no dropped frames, clean stop.

**Daylight trial run 29 August 2026, ~09:00-09:45.** Two independent sessions on the fixed firmware, both fully unattended over the dev bridge:

- **Trial 1** (`run_000053`, ~5 minutes): `img_1` (session start) and `img_320` (~5 min in) both showed the same **purple/magenta cast**, visually unchanged between the two - inconclusive on its own, so the trial was extended rather than concluded from 5 minutes.
- **Trial 2** (`run_000054`, ~30 minutes, matching the timeframe that showed clearing before the fix): `img_1` again showed the purple/magenta cast; `img_1650` (~27 minutes in) was **neutral white/grey** - the cast had cleared, on essentially the same timeline as before this fix (previously ~30 minutes for a green cast).

**Conclusion: the fix did not solve the problem, though its own mechanism worked exactly as designed.** The boot log confirmed correct AWB configuration and 85 real frames pumped during the 15 s warm-up (see below) - a substantial improvement over zero, but evidently still nowhere near enough for AWB to reach a converged state before the first retained frame. The cast is still present at session start, still takes on the order of ~30 minutes to clear, and - a new observation - **the cast's actual colour is not fixed**: green on 28 August, purple/magenta on both 29 August trials. That variability suggests whatever state AWB starts from at boot is itself inconsistent, not a single deterministic offset that a modest, fixed warm-up could reliably correct for.

**Not attempted further today, left as concrete next steps for whoever picks this up:**
1. Query `sensor_->status.awb_gain`/`aec_value`/related register fields at boot and periodically during a session (not just the on/off flags already logged) to see the actual convergence trajectory, rather than inferring it indirectly from JPEG output.
2. Consider a much longer active warm-up - real convergence takes roughly 1,600-1,800 real frames (~27-30 minutes at 1 FPS) based on both this and the prior finding, two orders of magnitude more than the 85 frames tried here. A warm-up that long is a real operational cost (delays the effective start of every session, even though it doesn't shrink the 3,600 s capture budget itself) and would need a product decision, not just an engineering one.
3. Consider seeding AWB from a fixed, pre-calibrated gain for typical enclosure conditions rather than relying on cold-start auto-convergence at all - trading some adaptability for a much faster, more predictable start.

## Finding: Wi-Fi radio activity breaks motion detection (21 August 2026)

While prototyping the device control app ([ADR 0001](adr/0001-device-hosted-control-app.md)), two live motion-mode sessions with the SoftAP running showed a 100% save rate — every scheduled motion check triggered a save, with scores clustering just above the threshold of 5 (5.8–12) rather than the wide, mostly-sub-threshold spread seen in earlier motion-mode testing. A same-scene control run with Wi-Fi disabled (`WIFI_CONTROL_DISABLED_FOR_TEST` build flag) and everything else identical showed normal discrimination: 131 of 132 checks correctly returned `motion_not_detected`, scores maxing at 3.57. Only Wi-Fi differed between the two conditions, so this is a confirmed effect, not a lighting or environmental confound (an initial lighting hypothesis was raised and specifically ruled out by this control test).

Suspected mechanism: SoftAP TX current draw introducing exposure micro-flicker that the motion score's whole-frame brightness correction does not fully cancel. Not yet confirmed at the electrical level. See [device-control-app-plan.md](device-control-app-plan.md) Phase 1 for mitigation options and current status — this blocks running Wi-Fi and motion-triggered capture concurrently until resolved. Retain-every-frame capture is unaffected.

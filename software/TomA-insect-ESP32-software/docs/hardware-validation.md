## Finding: `SD.totalBytes()` reports a wrong value on every normal (cold) boot (29 August 2026)

Found while adding a storage-remaining metric to the dashboard front page. `SdStorage::totalBytes()` (a thin wrapper over `SD.totalBytes()`) reports a value roughly double the card's actual capacity (`7,948,206,080` vs. the correct `3,653,238,784`, confirmed via the dev-bridge `DF` command on the same physical mount) - but only on the **very first `SD.begin()` call since power-on**. Any later, separate `SD.begin()` call in the same power cycle (e.g. the dev-bridge's `MOUNT` command, run after a session has stopped) reports correctly. The wrong value is stable for the entire session, not just the initial read - re-checked after a chunk promotion (~100 captures in) with no change. `SD.usedBytes()` is unaffected throughout.

Three fixes tried, all firmware-only, none successful - recorded so they are not retried without new information:
1. **Not an SPI clock effect.** Both the wrong cold-mount reading and the correct warm-mount reading were confirmed at the same negotiated 25 MHz.
2. **A throwaway `SD.begin()`/`SD.end()` cycle before the real mount** (hypothesis: "warm up" the reporting without changing real mount behaviour) - no effect, value unchanged.
3. **`SD.cardSize()` instead of `SD.totalBytes()`** - a completely different code path (`sdcard_num_sectors()`/`sdcard_sector_size()`, reading the card's own registers, versus `totalBytes()`'s `f_getfree()` call into FATFS volume metadata) - reproduced the identical wrong value. This is the most informative negative result: it points at the underlying SD driver's own card-geometry detection being wrong on a cold mount, not at anything in the Arduino-level FAT filesystem layer, which is beyond what could be safely investigated further without lower-level ESP-IDF tooling or physical access.

**Practical impact:** every normal deployment reads this value from a cold boot - nobody naturally triggers a second `SD.begin()` before looking at the dashboard - so this would be wrong in every real use case, not an edge case. The dashboard's storage-remaining metric was built and worked correctly end-to-end, but `DashboardWriter::writeSummary()` deliberately did not populate `sdTotalBytes`/`sdUsedBytes` until this was fixed, rather than ship a number known to be wrong. **Superseded 12 September 2026:** rather than leave the tile reading "Soon" indefinitely, it was replaced with a total-recorded-time metric derived from capture timestamps instead - see docs/next-session.md. The firmware bug itself is unchanged and still unfixed; only the dashboard-side placeholder is gone. Left as an open firmware/driver-level investigation for whoever has the tooling to go deeper (live heap/register debugging, or checking whether this is a documented erratum for this card/ESP-IDF SD driver combination).

## Incident: FAT32 root-directory corruption after normal power-off (21 August 2026)

After a successful motion-mode test run (`run_000002`, the shard-directory fix validation — 299 checks, 31 saved images, 0 storage errors during capture), the card was stopped normally by disconnecting the battery cable and moved to a card reader. On the next mount, Windows reported the volume as a healthy FAT32 filesystem (correct size, no dirty bit), but the root directory itself was corrupted: every real file and folder (`dashboard.html`, `config.json`, `raw/`, `images/`, `data/`, `system/`) had been replaced by a single garbled, zero-length pseudo-entry that both `attrib` and PowerShell's file APIs treated as a broken symbolic link.

This is first-hand confirmation of the FAT32 write-safety risk already flagged in `docs/next-session.md` and the project brief: the filesystem's own directory/FAT metadata is not written atomically, and the documented stop method (disconnect the battery cable) gives no opportunity for a controlled unmount. The firmware's per-frame atomic-rename writes protected individual images and CSV rows during the session itself (no corruption was ever observed while captures were running, across today's session or the prior one), but this incident shows the risk sits one level up, in the filesystem's own directory table, which firmware-level write discipline cannot fully protect against.

Recovery attempted: `chkdsk /f` repaired the volume and recovered 2,007 orphaned cluster fragments (275 MB) into `FOUND.000`. 1,913 of those fragments began with a valid JPEG signature, so most of the recovered data was genuine photo content, but the recovery was fragment-level (unordered ~32 KB clusters, most JPEGs span several), carried no filenames or session metadata, and only one fragment retained readable `captures.csv` header text. Given the run was this week's test data rather than irreplaceable field data, reconstruction was not attempted; the card was reformatted clean instead.

**Open follow-up:** this remains an unresolved hardware-level gap, not something firmware alone can fully close (see the physical power hold-up circuit note in the project brief). It also means a corrupted card is a real, observed failure mode for the pilot, not just a theoretical one — worth factoring into the one-hour endurance test and any operator-facing guidance on stopping the camera safely.

## Finding: one-hour pilot runs consistently fall ~10-15 images short of 3,600; dark-scene-JPEG-size theory tested and not confirmed (28 August 2026)

**Dark run** (`run_000041`), driven entirely over the serial [dev bridge](dev-bridge.md) while unattended: the card had drifted to a stale 5-minute trial `config.json` (`max_session_seconds: 300`) from earlier testing, corrected to the repository pilot default and applied with `reboot`. Ran its full `max_session_seconds: 3600`, self-finished cleanly, no reboot/storage error/corruption. **Captured 3,589/3,600** - 35 full shards plus a partial final shard (89 images). Averaged ~190 KB/image, well above the ~87 KB reference, in a dark room. Working theory at the time: larger, noisier dark-scene JPEGs push some per-frame writes over the 1,000 ms budget, and the schedule never fully catches up over an hour.

**Daylight run** (`run_000050`), same protocol, run after the room had light again: **captured 3,585/3,600** - *slightly worse*, not better, despite JPEGs averaging 87,656 bytes (right on the ~87 KB reference, confirming lighting was the reason the dark run's files were oversized). `interval_mean_ms=1004` (on target) but `interval_max_ms=2363` - a *larger* worst-case gap than the dark run's 2,085 ms. Both runs' stats came from the on-device `AUDIT` command (see [dev-bridge.md](dev-bridge.md)), which also confirmed `csv_completed` exactly matches the on-disk image count in both cases - the shortfall is real capture loss, not a logging/audit discrepancy.

**Conclusion: the dark-scene-JPEG-size theory is not confirmed.** Smaller files did not close the gap or reduce the worst-case interval - if anything both got slightly worse. The ~0.3-0.4% shortfall looks like a more fundamental, lighting-independent cadence issue (`AUDIT` only reports mean/max interval, not the full distribution or its correlation with individual frame write time, so the exact mechanism - occasional SD/filesystem housekeeping cost, chunk-promotion overhead, or something else - remains open). Worth revisiting once the write-path reduction work in `next-session.md`'s SD-performance section has progressed further, or with finer-grained per-frame instrumentation than `AUDIT` currently provides.

## Fix attempted: session-start white balance - did not resolve it (28 August-29 August 2026)

The user reported the session-start green cast (finding above) as a repeated problem, not a one-off. Investigating `src/camera_service.cpp` found the driver never explicitly configured AWB, relying entirely on `esp_camera_init()` defaults, and `src/main.cpp`'s 5-second camera warm-up was a bare `delay(kCameraWarmupMs)` - the sensor was never actually asked to produce a frame during that window. AWB/AEC algorithms converge on captured frames, not elapsed time, so a pure delay gives them zero iterations to work with; this is a strong candidate for why 5 seconds did nothing but ~1,800 real captures (30 minutes at 1 FPS) did.

**Fix:** `CameraService::initialiseCamera()` now explicitly calls `set_whitebal(1)`, `set_awb_gain(1)`, `set_wb_mode(0)` (auto, not a fixed preset) after every sensor init, and exposes `whiteBalanceStatus()` for boot-log diagnostics. `setup()`'s warm-up (`kCameraWarmupMs`, now 15,000) replaced the bare `delay()` with an active loop that calls `camera.capture()`/`camera.release()` repeatedly until the deadline, giving AWB/AEC real frames to converge on before the first frame is ever retained. Costs nothing against the 3,600 s capture budget - `session_started_ms` is only set after warm-up completes.

**Functionally verified 28 August 2026** (smoke test only, not a colour-quality trial - it was evening): built, flashed, and the boot log confirmed the mechanism works as intended - `awb=1 awb_gain=1 wb_mode=0` both before and after warm-up, and **85 real frames pumped** in 15 s (versus zero previously). A short test session then captured normally with no crashes, no dropped frames, clean stop.

**Daylight trial run 29 August 2026, ~09:00-09:45.** Two independent sessions on the fixed firmware, both fully unattended over the dev bridge:

- **Trial 1** (`run_000053`, ~5 minutes): `img_1` (session start) and `img_320` (~5 min in) both showed the same **purple/magenta cast**, visually unchanged between the two - inconclusive on its own, so the trial was extended rather than concluded from 5 minutes.
- **Trial 2** (`run_000054`, ~30 minutes, matching the timeframe that showed clearing before the fix): `img_1` again showed the purple/magenta cast; `img_1650` (~27 minutes in) was **neutral white/grey** - the cast had cleared, on essentially the same timeline as before this fix (previously ~30 minutes for a green cast).

**Conclusion: the fix did not solve the problem, though its own mechanism worked exactly as designed.** The boot log confirmed correct AWB configuration and 85 real frames pumped during the 15 s warm-up (see below) - a substantial improvement over zero, but evidently still nowhere near enough for AWB to reach a converged state before the first retained frame. The cast is still present at session start, still takes on the order of ~30 minutes to clear, and - a new observation - **the cast's actual colour is not fixed**: green on 28 August, purple/magenta on both 29 August trials. That variability suggests whatever state AWB starts from at boot is itself inconsistent, not a single deterministic offset that a modest, fixed warm-up could reliably correct for.

**Not attempted further on 29 August, left as concrete next steps for whoever picks this up:**
1. Query `sensor_->status.awb_gain`/`aec_value`/related register fields at boot and periodically during a session (not just the on/off flags already logged) to see the actual convergence trajectory, rather than inferring it indirectly from JPEG output. Still not attempted - the ESP-DL/esp32-camera source needed to confirm OV3660's actual gain register addresses isn't vendored into this project (headers only, no driver `.c` source), and guessing register numbers to `get_reg`/`set_reg` against real hardware was judged too risky to try blind.
2. Consider a much longer active warm-up - real convergence takes roughly 1,600-1,800 real frames (~27-30 minutes at 1 FPS) based on both this and the prior finding, two orders of magnitude more than the 85 frames tried here. A warm-up that long is a real operational cost (delays the effective start of every session, even though it doesn't shrink the 3,600 s capture budget itself) and would need a product decision, not just an engineering one.
3. Consider seeding AWB from a fixed, pre-calibrated gain for typical enclosure conditions rather than relying on cold-start auto-convergence at all - trading some adaptability for a much faster, more predictable start.

## Fix attempted: fast low-resolution warm-up mode (31 August 2026)

The owner's own diagnosis of the 29 August result: the 85-frame warm-up was rate-limited, not time-limited - it ran at the full QXGA capture resolution, so 15 s only bought ~5.7 fps. Proposed fix: warm up in a small, fast, still-colour sensor mode (not the existing grayscale motion-preview mode, since grayscale output may bypass the colour pipeline AWB needs), then switch to the real capture/preview mode once warmed - the same dual-resolution-mode pattern this project already uses for motion preview vs retained capture.

**Implemented:** `CameraService::configureWarmupSensor()` (QQVGA JPEG) and `restoreOperatingMode()` (switches back to whatever `begin()` would have selected). `setup()`'s warm-up block now switches to the fast mode, pumps for `kCameraWarmupMs`, reports the actual fps achieved, then restores the real mode before `session_started_ms` is set. `kCameraWarmupMs` reduced 15,000 → 10,000 to leave headroom for the two extra sensor reinits under a 15 s total, per the owner's request to get warm-up under 15 s.

**Measured 31 August 2026 (reboot + live serial capture over the dev bridge):**

```
camera warm-up pump complete: 138 frames in 10s (13.8 fps), awb=1 awb_gain=1 wb_mode=0
camera warm-up complete: switched back for the session (OV3660 ready for retained JPEG capture), awb=1 awb_gain=1 wb_mode=0
camera warm-up total wall time: 10756 ms
```

**Real improvement, but does not on its own reach convergence inside 15 s.** 13.8 fps is ~2.4x the QXGA rate (5.7 fps) - a smaller, more modest gain than hoped for from dropping all the way to QQVGA, which suggests JPEG encode time at QXGA was only part of the 29 August bottleneck; something else (sensor readout/exposure-integration timing at the fixed 20 MHz XCLK, most likely) is capping frame rate independent of resolution. At the measured 13.8 fps, reaching the ~1,600-1,800 frames the 29 August trial found necessary for full convergence would take roughly 2 minutes, not the previous ~27-30 minutes - a genuine ~15x reduction - but still far short of the owner's under-15-second target for full convergence. Total warm-up wall time (10,756 ms, including both sensor reinits) did land under 15 s as asked, it just doesn't fully converge white balance in that time.

**Not yet checked:** whether the ~2 minutes of QQVGA pumping this enables (if the warm-up window is lengthened rather than kept at 10 s) actually produces a materially better starting frame than the 29 August result, or whether it converges to a different, equally-wrong cast the way 29 August's purple/magenta did versus 28 August's green - this needs a real image comparison, not just the frame-count/fps numbers above, before calling it an improvement in output quality. Left as the immediate next step below.

**Follow-up trial, same session, second run (`run_000069`, ~4.5 minutes real time, 100 frames captured at the normal session cadence after warm-up):** `img_1` again showed the green cast; `img_35` (~35 s post-warm-up) had already flipped to the purple/magenta stage - reaching in under a minute what the 29 August trial hadn't reached even by its 5-minute checkpoint. But `img_50` and `img_100` (out to ~4.5 minutes total) show **no further change** - still the same purple/magenta, not neutral. **The fast warm-up sped up the first stage of the transition, not the whole thing.** Once the session's normal capture cadence takes over from the warm-up (~1 fps, per `interval_mean_ms=1037` in this run's `AUDIT`), the same frame-rate bottleneck the 29 August finding described reasserts itself - the 138 frames the warm-up bought are a small fraction of the ~1,600-1,800 needed in total, so most of the convergence work is still left to the slow part of the session. Consistent with the frame-count model throughout: total frames accumulated since boot by `img_100` here is only ~240 (138 warm-up + ~100 real captures), nowhere near the ~1,700 the 29 August finding measured as necessary.

**Conclusion: the fix is a genuine, real, measured improvement (reaches the purple/magenta stage in under a minute instead of several) but does not deliver the owner's under-15-second target, and by the numbers above it can't, not without either a much higher warm-up frame rate or a much longer warm-up window.** At the measured 13.8 fps ceiling, reaching all ~1,700 frames during warm-up (the only way to get full convergence before the session starts) needs roughly 2 minutes, not 15 seconds. This is being reported plainly rather than tuned further to look better - see options below.

**Options for whoever picks this up, none acted on yet beyond the two measurements above:**
1. **Accept 13.8 fps and lengthen the warm-up window** to the ~2 minutes the fps implies, instead of forcing it under 15 s - a real, measured, ~15x improvement over the previous ~30 minutes, even though it doesn't hit the owner's original 15 s target. This is a product trade-off (session start delayed by ~2 minutes, every session, in exchange for correct colour from frame 1) not an engineering one - matches the same kind of call flagged after the 29 August trial.
2. **Investigate whether XCLK/PCLK timing, or auto-exposure integration time in the current room's light level, is the real fps cap** - if so, a resolution below QQVGA won't help further, and the 13.8 fps figure may be close to this driver's ceiling regardless of frame size or scene brightness. Not tested: whether this ceiling is materially different in bright daylight vs. the (unrecorded) light level during this trial.
3. **Combine with option 3 from the 29 August finding (fixed calibrated gain)** - use the fast warm-up to get partway, then seed/lock a known-good gain rather than waiting for full auto-convergence either way. Probably the most promising route to actually hitting a 15 s target, since it sidesteps the frame-count requirement entirely instead of racing it.

## Seeded white balance: root cause found for why the fast warm-up didn't stick (31 August 2026)

The owner's own proposal, after the fast-warm-up result above: seed AWB from a known-good gain value (derived from the images already captured), then let it walk from that seed to whatever's optimal for actual current lighting during a short warm-up - rather than racing cold auto-convergence.

**Investigated the real driver source first** (`sensors/ov3660.c`, `espressif/esp32-camera`, fetched from GitHub) rather than guessing register addresses - confirmed manual R/G/B gain lives at `0x3400`/`0x3402`/`0x3404` (16-bit each), with a manual/auto latch at `0x3406`; these are the exact registers `set_wb_mode()`'s fixed presets (sunny/cloudy/office/home) already write, and are reachable through the sensor's own public `get_reg`/`set_reg` (mask > 0xFF routes through the 16-bit path). Added `CameraService::manualGainStatus()` (read) and `seedWhiteBalance()` (write gains, then re-enable auto so the seed is a starting point, not a lock).

**Direct on-device confirmation found the actual bug in the 31 August fast-mode design:** logged gain registers immediately before and after `restoreOperatingMode()`'s switch back to real capture mode. Before: `r=1065 g=1024 b=2174` (the fast-mode warm-up's own converged value). Immediately after the switch: **`r=1024 g=1024 b=1024`** - reset to hardware default. **Every `esp_camera_init()` call resets these registers**, so the entire fast-mode warm-up was being thrown away at the exact moment it mattered. This explains the `img_1` green cast seen in the fast-mode follow-up trial (worse than the purple/magenta it started from, because the reset landed on a *different* wrong default than either prior run's starting point).

**Consequence: the two-mode-switch design (configureWarmupSensor -> pump -> restoreOperatingMode) is self-defeating and has been disabled** (`fast_mode` hardcoded `false` in `setup()`, `configureWarmupSensor()`/`restoreOperatingMode()` still present on `CameraService` since they're independently correct, just not currently called this way). Whatever seeding scheme ships needs to apply the seed **after** the final mode is set, not before a switch that will erase it.

**Follow-up calibration, pumping continuously in the real QXGA capture mode (no further switch), 6 minutes / 2,003 frames:** gain plateaued at `r≈1056 g=1024 b≈2120` within the first ~10 s (57 frames) and stayed flat, noise only, for the entire remaining 350 s. **This is a second, independent, more surprising finding: it contradicts the earlier theory that AWB needs ~1,600-1,800 frames to converge.** If the register genuinely plateaus within seconds in a continuous session with no resets - and the pre-31-August retain-all capture path never switches modes between frames either, so this is the same condition the original 29 August real session ran under - then these three registers are not what was slowly changing over the ~27-30 minutes that trial's visible cast took to clear. Something else in the pipeline (auto exposure/AEC, a different ISP stage, or something not exposed via this register set at all) is the more likely actual driver of that slow change, not AWB gain as such.

**The decisive missing piece - whether the image captured at this plateaued QXGA state actually looks neutral - was not obtained.** The board dropped off USB entirely (`ping` fails with `FileNotFoundError`, Windows Device Manager shows the serial device present but `Unknown` status) moments after the calibration pump finished and before the card could be read. Two retries and a PnP disable/enable cycle (PowerShell) did not recover it; this needs a physical unplug/replug, which isn't possible remotely. **Left exactly here for whoever has physical access next** - the moment the board responds again, pulling `run_000075`'s first image is the very next step, and it directly decides whether the "seed with this plateaued value" plan is sound or whether the real cause is elsewhere. See `docs/next-session.md` priority item 0.

**Resumed once the board came back** (see next-session.md item 0 - a physical USB replug fixed it). Shortened the calibration to 30 s in the real capture mode (past the ~10 s plateau, no mode switch) and pulled the actual image: **`run_000078/img_1` is visually neutral** - grey/white, no meaningful colour cast, a clear confirmation that a no-reset pump in the real capture mode reaches a genuinely good state, fast.

**Shipped design:** `CameraService::seedWhiteBalance()` writes a starting gain directly onto the already-configured real capture sensor (no mode switch, so no reset risk), then a 12 s pump lets AWB walk from there. Seed values (`kWhiteBalanceSeedRedGain/Green/Blue` in `main.cpp`) taken from the `run_000078` measurement: `r=1055 g=1024 b=2100`. `configureWarmupSensor()`/`restoreOperatingMode()` (the broken two-mode design) removed from `CameraService` entirely - see its git history if the fast-mode approach is ever worth revisiting with the reset issue accounted for.

**Final on-device check (`run_000080`) was inconclusive, for a mundane reason: it had gone dark in the room by the time this test ran.** `img_1` is essentially black/noisy purple - normal sensor noise-floor behaviour in near-zero light, not a white-balance artefact. Gain walked from the seed to `r=1424 g=1024 b=1560` within the 12 s pump, a large swing consistent with AWB trying to average a scene with no real colour signal. **This does not undermine the design** - the daylight `run_000078` result is the real evidence the seed/approach works, gathered in the same room earlier the same session - but it means the *shipped* seed-and-walk path itself has not yet been visually confirmed in daylight. **Next step: re-run this exact check once it's light again** (reboot, let the 12 s warm-up finish, pull the first retained image, confirm it looks neutral) before calling this done.

**State the firmware is currently in:** committed as described above - `kCameraWarmupMs = 12000`, seed-then-walk, no mode switch. Builds clean, all 7 pinned contract checks pass.

## Finding: Wi-Fi radio activity breaks motion detection (21 August 2026)

While prototyping the device control app ([ADR 0001](adr/0001-device-hosted-control-app.md)), two live motion-mode sessions with the SoftAP running showed a 100% save rate — every scheduled motion check triggered a save, with scores clustering just above the threshold of 5 (5.8–12) rather than the wide, mostly-sub-threshold spread seen in earlier motion-mode testing. A same-scene control run with Wi-Fi disabled (`WIFI_CONTROL_DISABLED_FOR_TEST` build flag) and everything else identical showed normal discrimination: 131 of 132 checks correctly returned `motion_not_detected`, scores maxing at 3.57. Only Wi-Fi differed between the two conditions, so this is a confirmed effect, not a lighting or environmental confound (an initial lighting hypothesis was raised and specifically ruled out by this control test).

Suspected mechanism: SoftAP TX current draw introducing exposure micro-flicker that the motion score's whole-frame brightness correction does not fully cancel. Not yet confirmed at the electrical level. See [device-control-app-plan.md](device-control-app-plan.md) Phase 1 for mitigation options and current status — this blocks running Wi-Fi and motion-triggered capture concurrently until resolved. Retain-every-frame capture is unaffected.
